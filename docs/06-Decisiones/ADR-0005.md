# ADR-0005: Testcontainers para tests de integración

- **Estado:** Aceptada
- **Fecha:** 2026-08-08
- **Decisión:** Los tests de integración usan Testcontainers con PostgreSQL real (`postgres:16-alpine`) en un contenedor compartido por toda la suite, conectado vía `@ServiceConnection`. Se descarta H2 y las conexiones a BD externas desde env vars.
- **Opciones descartadas:** H2 en modo PostgreSQL, PostgreSQL local vía env vars (`DB_URL`)

## Contexto

Los tests de integración (`@SpringBootTest`) usaban el perfil `local` y se conectaban a la BD apuntada por las env vars (`DB_URL`, `DB_USERNAME`, `DB_PASSWORD`) — en el entorno del desarrollador una instancia Supabase remota. Esto es frágil: los tests dependen de credenciales de entorno, corren contra datos que no controlan, y exponen la BD real a datos de prueba. Además el flujo de aprovisionamiento de tenant crea schemas físicos (ADR-0001, ADR-0004) que requieren un PostgreSQL real: H2 no replica fielmente DDL como `CREATE SCHEMA`, índices parciales, triggers plpgsql ni `gen_random_uuid()`.

## Opciones consideradas

### 1. Testcontainers con PostgreSQL (seleccionada)

`PostgreSQLContainer` estático y compartido en `BaseIntegrationTest`, con `@ServiceConnection` que hace que la autoconfiguración del DataSource use el contenedor por encima de cualquier propiedad (`spring.datasource.url`, env vars). Un único contenedor para toda la suite; los schemas de tenant se crean/destruyen por test.

**Ventajas:**
- PostgreSQL real: valida DDL, triggers, índices parciales y migraciones Flyway exactamente como producción
- Reproducible y sin credenciales externas: no depende de env vars ni de BD remotas
- Cada corrida arranca desde un estado limpio (Flyway migra el contenedor al arrancar)
- Detectó un bug real: el trigger `fn_document_owner_permission` dependía del `search_path` de la conexión

**Desventajas:**
- Requiere Docker corriendo para ejecutar tests
- Costo de arranque del contenedor (aceptable, compartido entre clases)

### 2. H2 en modo PostgreSQL

**Ventajas:** sin Docker, rápido.
**Desventajas:** no soporta fielmente `CREATE SCHEMA`, índices parciales `WHERE`, triggers plpgsql ni funciones como `gen_random_uuid()` — el flujo de multi-tenancy no se puede validar; falsos positivos.

### 3. BD externa vía env vars (status quo)

**Desventajas:** depende de credenciales de entorno, corre contra datos de un entorno real, no reproducible en CI, riesgo de contaminar BD de desarrollo.

## Decisión

Se adopta Testcontainers. Un `PostgreSQLContainer` estático en `BaseIntegrationTest` se inicia manualmente (bloque `static`) para que **un solo contenedor** sobreviva a todas las clases de test y a los múltiples contextos de Spring (evita que la extensión `@Testcontainers` lo detenga tras la primera clase). `@ServiceConnection` conecta la app al contenedor ignorando `spring.datasource.*` y env vars.

## Consecuencias

- Nueva dependencia de test: `spring-boot-testcontainers`, `org.testcontainers:postgresql`, `org.testcontainers:junit-jupiter` (versiones vía `testcontainers-bom`).
- `src/test/resources/docker-java.properties` con `api.version=1.44`: docker-java de Testcontainers 1.21.x fija API 1.32 por defecto y Docker Engine ≥ 25 (aquí 29.x) exige API ≥ 1.44; sin este archivo Testcontainers no conecta. Alternativa futura: migrar a Testcontainers 2.x cuando esté disponible, que sube el default.
- Los 3 tests de integración pasan a extender `BaseIntegrationTest` (perfil `test`); el perfil `local` queda solo para ejecución manual de la app.
- `application-test.yaml` aporta defaults de datasource para resolver placeholders sin env vars (CI).
- `mvn test` requiere Docker corriendo.
