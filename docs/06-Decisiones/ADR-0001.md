# ADR-0001: Schema-per-tenant como estrategia de multi-tenancy

- **Estado:** Aceptada
- **Fecha:** 2024-07 (inferido del commit inicial)
- **Decisión:** Schema-per-tenant
- **Opción descartada:** Database-per-tenant, Row-level security

## Contexto

MultiVault es un sistema de gestión documental que debe alojar datos de múltiples clientes (tenants) con aislamiento completo. Se necesita una estrategia de multi-tenancy que garantice que los datos de un cliente no sean accesibles por otro.

## Opciones consideradas

### 1. Schema-per-tenant (seleccionada)

Cada tenant tiene su propio schema PostgreSQL. Las tablas compartidas viven en el schema `public`.

**Ventajas:**
- Aislamiento físico completo a nivel de base de datos
- No requiere modificar queries con cláusulas `WHERE tenant_id = ?`
- Backup/restore por tenant más sencillo
- Posibilidad de migraciones independientes por tenant

**Desventajas:**
- Límite práctico de schemas (PostgreSQL maneja bien hasta ~10,000)
- Mayor complejidad en la gestión de conexiones
- Migraciones Flyway deben ejecutarse en cada schema

### 2. Database-per-tenant

**Desventajas:**
- Mayor overhead de conexiones
- Pooling más complejo
- Backup/restore más pesado

### 3. Row-level security (RLS)

**Desventajas:**
- Riesgo de fuga de datos por error en políticas
- Performance impact en queries
- Más complejidad en migraciones y desarrollo

## Decisión

Se adopta **Schema-per-tenant** porque:
1. El proyecto ya tiene el diseño implementado en SQL (`tenant.schema_name`, `tenant_schema.sql`)
2. Proporciona el máximo aislamiento
3. Es la estrategia más probada para sistemas B2B con pocos cientos de tenants

## Consecuencias

- La aplicación debe crear schemas dinámicamente al aprovisionar un nuevo tenant
- Se necesita un mecanismo para resolver el tenant actual en cada request (Connection Provider)
- Las migraciones Flyway deben ejecutarse en el schema público y replicarse en cada schema de tenant
- Las conexiones JDBC deben usar `search_path` para apuntar al schema correcto
