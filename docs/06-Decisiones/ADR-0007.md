# ADR-0007: JJWT con codec JSON Jackson 3 propio (sin jjwt-jackson)

- **Estado:** Aceptada
- **Fecha:** 2026-08-09
- **Decisión:** Usar `jjwt-api` + `jjwt-impl` con un `Serializer`/`Deserializer` propio basado en Jackson 3 (`tools.jackson`). No usar `jjwt-jackson`.
- **Opciones descartadas:** `jjwt-jackson` (arrastra Jackson 2 al classpath y rompe la persistencia JSON de Hibernate), `jjwt-gson` (introduce Gson como segundo JSON library), forzar `hibernate.format_mapper` a Jackson 3 (mantiene Jackson 2 deprecado y acopla a internals de Hibernate).

## Contexto

El proyecto corre Spring Boot 4.1, que usa Jackson 3 (`tools.jackson.*`). Al agregar `jjwt-jackson:0.13.0` para preparar la autenticación JWT, este arrastra `com.fasterxml.jackson.core:jackson-databind` (Jackson 2) de forma transitiva. Es la única versión publicada de JJWT; el soporte de Jackson 3 está en PR sin release (jwtk/jjwt#1038).

Con Jackson 2 presente, Hibernate 7.4 lo detecta y usa su `JacksonJsonFormatMapper` (el de Jackson 2) para mapear tipos JSON. La entidad `AuditLog.metadata` está tipada como `tools.jackson.databind.JsonNode` (Jackson 3) con `@JdbcTypeCode(SqlTypes.JSON)`, así que al persistir el mapper de Jackson 2 no puede deserializar ese nodo: `InvalidDefinitionException`.

El `save` ocurre dentro del listener `AuditLogEventListener#on`, anotado con `@TransactionalEventListener(AFTER_COMMIT)`. Spring ejecuta ese listener dentro de `TransactionSynchronization.afterCommit`, cuyas excepciones **captura y solo loguea** sin propagarlas. Por eso el build no mostraba ningún error: los tests de auditoría fallaban con assertions limpias (0 filas). `mvn clean install` fallaba en `AuditEventPublishingTest.persistsAuditLogAfterSuccessfulTransaction` y `TenantProvisioningTest.createsTenantWithSchemaUsageApiKeyAndAudit`.

## Opciones consideradas

### 1. Codec JSON propio sobre Jackson 3 (seleccionada)

`jjwt-api` + `jjwt-impl` y dos componentes que implementan `io.jsonwebtoken.io.Serializer<Map<String, ?>>` y `io.jsonwebtoken.io.Deserializer<Map<String, ?>>` usando el `ObjectMapper` de Spring (Jackson 3).

**Ventajas:**
- Quita `jackson-databind` 2.x del classpath: Hibernate vuelve al mapper Jackson 3 y la auditoría persiste
- Un solo JSON library en todo el proyecto (Jackson 3), sin depender de la pila deprecada de Jackson 2 en Boot 4
- El codec reutiliza el `ObjectMapper` autoconfigurado de Spring (misma configuración de mixins/serializers que el resto de la app)

**Desventajas:**
- Pequeño código de adaptación (~50 líneas)
- Toda construcción/parseo de JWT debe registrar el codec explícitamente (`serializeToJsonWith` / `deserializeJsonWith`)

### 2. `jjwt-gson`

Reemplazar `jjwt-jackson` por `jjwt-gson`.

**Ventajas:**
- Swap simple en el pom; Gson no choca con Jackson

**Desventajas:**
- Introduce un segundo JSON library solo para JWT, inconsistente con el resto del proyecto
- Gson y Jackson 3 producen representaciones/errores distintos (números grandes, fechas) que pueden sorprender al validar claims

### 3. Mantener `jjwt-jackson` + forzar `hibernate.format_mapper=org.hibernate.type.format.jackson.Jackson3JsonFormatMapper`

**Ventajas:**
- Cambio mínimo, sin tocar el pom

**Desventajas:**
- Jackson 2 sigue en el classpath (soporte deprecado en Spring Boot 4, con riesgo de choques futuros al subir versiones)
- Acopla la config a una clase interna de Hibernate; cualquier cambio de la SPI rompe la persistencia silenciosamente

## Decisión

Se adopta la opción 1. Se elimina `jjwt-jackson` del pom y se agregan `dev.achiri.multivault.infrastructure.security.codec.JwtJackson3Serializer` y `JwtJackson3Deserializer`, ambos `@Component` que inyectan el `ObjectMapper` de Jackson 3 y envuelven errores en `SerializationException`/`DeserializationException`. El build vuelve a pasar con los 32 tests en verde.

## Consecuencias

- El classpath deja de contener `com.fasterxml.jackson.core:jackson-databind`; solo queda `jackson-annotations` 2.21 (compartido por diseño entre Jackson 2 y 3 en Boot 4)
- Todo uso futuro de JJWT (ej. `JwtDecoder` multi-issuer) debe registrar el codec: `Jwts.builder().serializeToJsonWith(serializer)` y `Jwts.parser().deserializeJsonWith(deserializer)`
- No hay `jjwt-jackson` en el pom: sin el codec, JJWT no encontraría serializer automático en el classpath
- Al actualizar JJWT a una versión con soporte Jackson 3 nativo (0.14+/futura), reevaluar el uso de `jjwt-jackson`
