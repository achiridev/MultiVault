# ADR-0009: Ciclo de vida de tenants (cancelación, suspensión, reactivación)

- **Estado:** ACEPTADA
- **Fecha:** 2026-08-17
- **Decisión:** Implementar `TenantLifecycleService` con transiciones de estado válidas y efectos colaterales controlados
- **Opciones descartadas:** Endpoints separados para cada operación, lógica inline en TenantService

## Contexto

El enum `TenantStatus` ya definía `CANCELLED` y `SUSPENDED` pero no existía lógica para gestionar estas transiciones. Se necesitaba un mecanismo formal para cancelar, suspender y reactivar tenants con efectos colaterales controlados (suscripción, API keys, miembros).

## Opciones consideradas

### Opción 1: Endpoints separados

`POST /tenants/{id}/cancel`, `POST /tenants/{id}/suspend`, `POST /tenants/{id}/reinstate`

**Ventajas:**
- API más explícita y RESTful
- Cada operación tiene su propio DTO de request

**Desventajas:**
- Duplicación de lógica de validación de transiciones
- Tres endpoints para una misma preocupación (gestión de estado)
- Difícil de mantener si se agregan nuevos estados

### Opción 2: Endpoint único con state machine

`PUT /tenants/status` con body `{ "status": "CANCELLED", "reason": "..." }` (la ruta es service-to-service, solo credencial SERVICE y sin `{tenantId}`, ver ADR-0012)

**Ventajas:**
- Un solo punto de entrada para todas las transiciones
- Validación centralizada de transiciones
- Fácil de extender con nuevos estados
- DTO consistente para request/response

**Desventajas:**
- Menos explícito en la URL (no dice qué operación se hace)
- Requiere validación del estado solicitado

## Decisión

**Opción 2: Endpoint único con state machine.** Se implementa `TenantLifecycleService.updateStatus()` que:
1. Valida la transición contra un mapa de transiciones permitidas
2. Aplica los efectos colaterales según la operación (cancel/suspend/reinstate)
3. Registra auditoría con la acción correspondiente
4. Devuelve un `TenantStatusResponse` con el estado anterior y actual

`CANCELLED` es terminal: no admite transiciones de salida. `SUSPENDED` puede transicionar a `ACTIVE` (reinstate) o `CANCELLED`. La reactivación no reactiva API keys revocadas; el usuario debe crear nuevas.

## Consecuencias

- **Positivas:** Transiciones centralizadas, efectos colaterales consistentes, auditoría completa, fácil de testear
- **Negativas:** El endpoint no es autoexplicativo (requiere documentación clara), la lógica de reactivación es asimétrica (keys no se reactivan)
- **Neutra:** Se agrega `EstadoTransicionInvalidoException` para transiciones inválidas (409 Conflict)
