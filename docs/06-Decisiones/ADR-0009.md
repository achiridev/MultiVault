# ADR-0009: Multi-tenancy en Hibernate con `search_path` sobre pool único

- **Estado:** Aceptada
- **Fecha:** 2026-08-12
- **Decisión:** Las consultas JPA se enrutan al schema del tenant con `hibernate.multiTenancy=SCHEMA`, un `MultiTenantConnectionProvider` que hace `SET search_path` sobre un pool único (HikariCP) y un `CurrentTenantIdentifierResolver` que lee el tenant desde un `TenantContext` (ThreadLocal). Las tablas públicas se cualifican explícitamente con `@Table(schema = "public")`.
- **Opciones descartadas:** pool de conexiones por tenant, `TenantSchemaMapper` nativo de Hibernate 7.

## Contexto

ADR-0001 definió schema-per-tenant y ADR-0004 el aprovisionamiento físico del schema. Quedaba pendiente el mecanismo para que las consultas JPA caigan en el schema del tenant correcto. Los principals de seguridad ya exponen `tenantId` (`TenantUserPrincipal` para JWT, `ApiKeyPrincipal` para API key), y ADR-0001 ya comprometía: "Las conexiones JDBC deben usar `search_path` para apuntar al schema correcto". Además, `ddl-auto: validate` valida las entidades contra `public` y las tablas por-tenant se excluyen vía `TenantSchemaFilterProvider` porque no existen en `public`.

El proyecto usa Hibernate 7.4 (Spring Boot 4.1), que ofrece tanto el API clásico (`CurrentTenantIdentifierResolver` + `MultiTenantConnectionProvider`) como un `TenantSchemaMapper` nuevo.

## Opciones consideradas

### 1. `search_path` sobre pool único (seleccionada)

`hibernate.multiTenancy=SCHEMA` con un resolver que devuelve el `schema_name` del `TenantContext`, y un connection provider que toma una conexión del pool único y ejecuta `SET search_path TO <schema>` antes de entregarla. Al liberarla, resetea `search_path` a `public` para no fugar el schema del tenant en el pool. Las tablas del schema público se cualifican con `@Table(schema = "public")` para que no dependan del `search_path`; las tablas por-tenant se dejan sin schema y resuelven por `search_path`.

**Ventajas:**
- Coherente con ADR-0001 y con el diseño ya implementado
- Un solo pool de conexiones: sin overhead de conexiones ni tuning por tenant
- El aislamiento no depende de nombres de tabla (las públicas están cualificadas explícitamente, sin fallthrough frágil a `public`)
- API Hibernate estable y muy probada en producción

**Desventajas:**
- Mutación del estado de la conexión (`search_path`): hay que resetear en el release, o el pool contamina conexiones entre tenants
- `@Async`/hilos sin contexto pierden el tenant (misma limitación en todas las opciones salvo pasar el tenant explícitamente)

### 2. Pool de conexiones por tenant

`AbstractDataSourceBasedMultiTenantConnectionProviderImpl` con un `DataSource` por tenant.

**Ventajas:** conexión siempre dedicada al tenant; sin reset de estado.

**Desventajas:** un HikariCP por tenant (límite de conexiones, tuning y monitoreo por tenant); el aprovisionamiento de schema necesita crear el DataSource en runtime; contradice el compromiso de `search_path` de ADR-0001.

### 3. `TenantSchemaMapper` nativo de Hibernate 7

Hibernate 7 puede calificar automáticamente las tablas con el schema del tenant (`org.hibernate.context.spi.TenantSchemaMapper`), sin mutar conexiones.

**Ventajas:** no toca la conexión; API nueva y limpia.

**Desventajas:** API reciente con menos evidencia en producción; la calificación automática de schema requiere validar el comportamiento con `ddl-auto: validate` y las entidades públicas; se aleja del compromiso explícito de `search_path` de ADR-0001.

## Decisión

Se adopta la opción 1: `search_path` sobre pool único.

- `hibernate.multiTenancy=SCHEMA`, `hibernate.tenant_identifier_resolver` y `hibernate.multi_tenant_connection_provider` en `application.yaml`.
- `TenantContext` (ThreadLocal) guarda el `schema_name`; lo setea `TenantContextFilter` tras la autenticación (después de los filtros JWT/API key, para que la validación del token y el upsert de `tenant_member` corran contra `public`) y lo limpia en `finally`.
- Entidades públicas: `@Table(name = "x", schema = "public")` (aditivo, sin cambio de comportamiento).
- `TenantSchemaFilterProvider` se mantiene: el `validate` de arranque corre contra la conexión `any` (schema `public`) y las tablas por-tenant no existen ahí.

## Consecuencias

- Resolver con contexto vacío → `null` → conexión `any` (schema `public`): los requests sin autenticación y las operaciones públicas siguen funcionando sin cambios.
- **Hibernate 7 exige un identificador de tenant no nulo al abrir una Session**: el contexto vacío se mapea al sentinela `public` (`CurrentTenantIdentifierResolverImpl.PUBLIC_SCHEMA`), que el connection provider trata como la conexión `any` (sin `SET search_path`). El `TenantContext` sigue guardando `null` para "sin tenant"; el mapeo ocurre en el resolver.
- `releaseConnection`/`releaseAnyConnection` ejecutan `SET search_path TO public` antes de cerrar para no fugar el schema del tenant en el pool.
- Costo por request: un lookup `tenant.schema_name` (vía `TenantRepository`) al resolver el tenant desde el principal. Optimizable con caché Redis si es necesario.
- Hilos `@Async` no heredan `TenantContext`; operaciones asíncronas por-tenant deberán setearlo explícitamente (fuera de alcance hoy).
- `supportsAggressiveRelease()` → `false` para no liberar la conexión en mitad de la transacción.
- El `storageKey` de las versiones de documento lo genera la app como `{schema}/{documentId}/{versionNumber}/{checksum}` (flujo metadata-only; el contenido binario queda pendiente de un ADR de storage).
- Sin cambios de migraciones Flyway ni de esquema SQL.
