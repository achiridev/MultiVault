# ADR-0011: El JWT de tenant exige API key; autorización por scopes

- **Estado:** Aceptada
- **Fecha:** 2026-08-29
- **Decisión:** Un JWT de tenant-membership solo autentica si viene acompañado de una API key STANDARD del mismo tenant. La autorización por endpoint se hace con scopes (`SCOPE_<scope>`) vía method security, no por URL en `SecurityConfig`.
- **Opciones descartadas:** Permitir JWT puro con acceso total; exigir scopes en `authorizeHttpRequests` por path.

## Contexto

El modelo de autenticación ya distinguía SERVICE (M2M, autentica solo) y STANDARD ("la app exige JWT junto a la key"). Sin embargo, `JwtAuthenticationFilter` autenticaba un JWT válido **sin** exigir la key STANDARD, así que un request con solo `Authorization: Bearer <jwt>` entraba a endpoints protegidos con authorities vacías. La intención de diseño era asimétrica: una key necesita JWT, pero el JWT no necesitaba key.

Además, los scopes de `api_key.scopes` (TEXT[]) se propagaban a `SCOPE_<scope>` en el SecurityContext pero nunca se evaluaban: `SecurityConfig` solo exigía `authenticated()` y no existía `@EnableMethodSecurity`. Un SERVICE key con `scopes = []` accedía a todo, y una key con `documents:read` podía escribir documentos.

## Opciones consideradas

### 1. JWT nunca solo + scopes vía method security (seleccionada)

- `JwtAuthenticationFilter` no autentica si el request no trae key STANDARD del mismo tenant (401).
- `@EnableMethodSecurity` + `@PreAuthorize("hasAuthority('SCOPE_...')")` en los controllers como punto único de autorización por scope.
- Los JWT de platform_user (staff interno, pendiente) quedan fuera de este filtro: su issuer no coincide con ningún tenant, por lo que serán autenticados por un `PlatformUserAuthenticationProvider` dedicado.

**Ventajas:**
- Cierra la brecha "JWT puro con acceso total" y hace los scopes efectivos
- El enforcement vive junto al recurso (controller), no en rutas frágiles de `SecurityConfig`
- La combinación STANDARD+JWT ya posicionaba las authorities en el contexto; solo faltaba evaluarlas

**Desventajas:**
- Cambio de comportamiento: todo cliente debe enviar una key (STANDARD en `X-API-Key` o SERVICE en `Authorization`) para acceder a endpoints protegidos
- Un `@PreAuthorize` sin scope la deja la regla "autenticado" vigente como fallback

### 2. Exigir scopes por URL en `authorizeHttpRequests`

**Ventajas:**
- Sin `@PreAuthorize`

**Desventajas:**
- Reglas por path difíciles de mantener con la combinación STANDARD+JWT y el routing por tenant
- No escala a permiso por recurso (p.ej. permisos por documento)

## Decisión

Se adopta la opción 1.

- Un JWT de tenant solo autentica si existe key STANDARD en el request (`STANDARD_API_KEY_ATTR`) y `tenantId` coincide con el del JWT. Sin key → el request sigue sin autenticar → 401 (`RestAuthenticationEntryPoint`).
- `SecurityConfig` gana `@EnableMethodSecurity`; los controllers declaran el scope requerido por endpoint.
- Vocabulario: `recurso:accion`, con wildcards `recurso:*` y `*` (admin total) disponibles si se necesitan.
- `GlobalExceptionHandler` mapea `AccessDeniedException` → 403 JSON (antes el catch-all lo convertía en 500).

## Consecuencias

- `Authorization: Bearer <jwt>` solo → 401 (a menos que sea un futuro JWT de platform_user, que usará su propio mecanismo de auth)
- Scopes efectivos en los endpoints implementados: `documents:write` (crear documento/versión), `documents:read` (leer documento), `tenant:settings:write` (identity-provider y status)
- SERVICE y STANDARD keys son ahora least-privilege: un scope faltante responde 403
- `@WithMockUser` en tests debe declarar `authorities = "SCOPE_..."` para los endpoints con scope
- Cuando exista el endpoint de creación de API keys, validar los scopes contra un catálogo fijo (hoy `Scopes`, ver ADR-0012) en BD (constraint/check); la key inicial ya no está "sin scopes": nace como SERVICE con scope `*` (ADR-0012), por lo que no se agrega migración hoy
