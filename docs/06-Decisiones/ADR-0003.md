# ADR-0003: Auditoría vía eventos de aplicación (AFTER_COMMIT)

- **Estado:** Aceptada
- **Fecha:** 2026-08-06
- **Decisión:** Auditoría desacoplada con `ApplicationEventPublisher` + `@TransactionalEventListener(AFTER_COMMIT)` + transacción `REQUIRES_NEW`; todo el sistema audita publicando `AuditEvent`
- **Opciones descartadas:** AOP con anotación `@Audited`, registro directo desde servicios, Spring Data Envers

## Contexto

`audit_log` ya existe en el schema público (WORM: insert-only, sin `updated_at`). Todo el sistema debe auditar (crear organización, borrar documento, revocar key, suscribir, ...). Los servicios no deben acoplarse a la persistencia del log: el registro de auditoría no puede hacer fallar la operación de negocio, y solo debe persistirse si la transacción de negocio commiteó.

## Opciones consideradas

### 1. Eventos de aplicación + AFTER_COMMIT (seleccionada)

El productor publica un `AuditEvent` inmutable (record con builder); un `AuditEventPublisher` envuelve `ApplicationEventPublisher`; `AuditLogEventListener` escucha con `@TransactionalEventListener(phase = AFTER_COMMIT)` y persiste en transacción `REQUIRES_NEW`.

**Ventajas:**
- Productores desacoplados del storage (WORM): solo conocen el evento
- AFTER_COMMIT garantiza que solo se auditan operaciones que commitearon
- `REQUIRES_NEW` aísla el INSERT del log: un fallo de auditoría no revierte el negocio
- Punto único de emisión (`AuditEventPublisher`) permite migrar a Outbox/`@Async`/bus sin tocar productores
- Sin dependencias nuevas (Spring Core/TX)

**Desventajas:**
- Al estar en la misma JVM, el listener comparte ciclo de vida del proceso (un crash entre commit y listener pierde el log)
- Requiere que los productores recuerden publicar el evento

### 2. AOP con anotación `@Audited`

Anotar métodos para auditar automáticamente vía aspecto.

**Ventajas:** cero fricción por cada nuevo caso.
**Desventajas:** requiere dependencia AOP (`spring-boot-starter-aop`), el aspecto necesita contexto de actor/recursos vía SpEL, oculta el evento, debug difícil. Se puede añadir después si el patrón evento-a-evento no escala.

### 3. Registro directo desde servicios (`auditLogRepository.save`)

**Ventajas:** simple.
**Desventajas:** acopla servicios al storage, duplica mapeo en cada llamada, fácil de omitir, acopla la vida del log a la tx del negocio.

### 4. Spring Data Envers

**Ventajas:** auditoría automática de cambios por entidad.
**Desventajas:** no aplica: el diseño de `audit_log` es orientado a eventos de negocio (acciones y recursos), no diffs de entidades; dependencia nueva y rigidez en el esquema.

## Decisión

Se adopta el patrón de eventos de aplicación. Un `AuditEvent` genérico con builder (`actorType` default `SYSTEM`, `metadata` default `{}`, `occurredAt` default `now()`) es la única moneda para auditar; `AuditEventPublisher.publish` es el único punto de emisión. El listener `AFTER_COMMIT` + `REQUIRES_NEW` convierte el evento en `AuditLog` y persiste en `audit_log`. Todo lo demás del sistema (tenant, document, api_key, ...) audita publicando `AuditEvent`, nunca escribiendo `AuditLog` directo.

## Consecuencias

- Nuevo paquete `dev.achiri.multivault.audit` con `model/`, `repository/`, `event/`.
- `AuditLog` extiende `BaseEntity` (sin `DateAudit`: la tabla no tiene `updated_at`); `created_at` con `@CreatedDate`.
- `metadata JSONB` → `tools.jackson.databind.JsonNode` con `@JdbcTypeCode(SqlTypes.JSON)` (Jackson 3 en Boot 4).
- `ip_address INET` → `java.net.InetAddress` con `@JdbcTypeCode(SqlTypes.INET)` (soporte nativo Hibernate 7; evita el cast varchar→inet).
- El `REVOKE` de UPDATE/DELETE a nivel de BD para el rol de la app sigue pendiente (docs/Seguridad.md).
- Si el volumen crece, migrar `AuditEventPublisher` a `@Async` o patrón Outbox sin tocar productores.
