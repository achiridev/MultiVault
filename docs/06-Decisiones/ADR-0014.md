# ADR-0014: Resolución estricta de clave JWKS por `kid`

- **Estado:** Aceptada
- **Fecha:** 2026-10-03
- **Decisión:** `MultiIssuerJwtDecoder` exige match exacto de `kid` contra el JWKS del issuer. Si el header trae `kid` y no hay coincidencia tras un evict + refetch, el JWT se rechaza. El fallback a "la primera clave del JWKS" se elimina. Para tokens **sin** `kid` solo se acepta un JWKS con exactamente una clave RSA.
- **Opciones descartadas:** fallback a la primera clave del JWKS; probar todas las claves del JWKS secuencialmente; cachear la clave resuelta cuando el token no trae `kid`.

## Contexto

`resolvePublicKey` seleccionaba la clave con `.orElse(entries.get(0))`. Cuando el `kid` del header no coincidía con ninguna entrada del JWKS —o directamente no venía, porque `readKeyId` devuelve `""` para un nodo ausente y ningún JWK tiene `kid` vacío— la verificación continuaba con la clave en posición 0 del array.

Esto no constitutes un bypass: la firma se sigue validando contra esa clave y un fallo produce `SignatureException` → 401. Los problemas reales eran otros:

1. **Cache-stampede amplificable.** `verifyWithRetry` hace `JwksProvider.evict` + `fetch` (HTTP al IdP, `connectTimeout` 5s / `timeout` 10s) ante cualquier fallo. Con el fallback, un request **no autenticado** con un `kid` arbitrario entraba siempre a ese camino: evict del caché `jwks` compartido + refetch contra el IdP del tenant. El backend quedaba como amplificador hacia un tercero.
2. **Retry mal ubicado.** `verifyWithRetry` solo capturaba `SignatureException`, pero `resolvePublicKey` lanzaba `InvalidJwtException` en "JWKS sin claves", "kty no soportado" y "clave JWKS inválida". Esas rutas **nunca refrescaban el caché**: un JWKS stale sin la clave nueva moría sin evict. Además el fallback consumía el único reintento verificando contra una clave que se sabía equivocada.
3. **No determinismo.** `entries.get(0)` depende del orden del array JSON que devuelve el IdP. El mismo token podía aceptarse o rechazarse según cómo el IdP serializara sus claves.
4. **Ambigüedad de procedencia.** Se aceptaba un token cuyo `kid` no correspondía a la clave que lo validó, contradiciendo el log de auditoría.

## Opciones consideradas

### 1. Match estricto de `kid` con evict + un refetch (seleccionada)

`kid` presente → filtrar por match exacto; si no hay, `UnknownKeyException` → evict + refetch una vez → si sigue sin match, `InvalidJwtException("kid no encontrado en JWKS: ...")`. `kid` ausente → exigir exactamente una clave RSA en el JWKS.

**Ventajas:**
- Alineado con el estándar de facto: `NimbusJwtDecoder`, `jose4j`, `node-jose` y `python-jose` exigen match cuando `kid` está presente.
- Un token con `kid` basura muere en memoria tras un lookup en Redis, sin refetch al IdP.
- El evict+retry cubre el caso real de rotación con caché stale, que era el propósito original del mecanismo.
- La cryptography y el `kid` coinciden siempre: la auditoría es inequívoca.

**Desventajas:**
- Un token sin `kid` contra un JWKS multi-clave se rechaza. Es el comportamiento correcto (no hay forma de elegir sin ambigüedad) pero es un cambio observable: 401 donde antes había 200.
- Un `kid` mal sincronizado que antes pasaba inadvertido ahora se expone como 401.

### 2. Probar todas las claves del JWKS secuencialmente

Ante `kid` desconocido, verificar la firma contra cada RSA del JWKS hasta que una cuadre.

**Desventajas:**
- Multiplica el trabajo criptográfico por el número de claves en el peor caso, sobre un input controlado por el atacante.
- La complejidad sigue siendo O(n) verificaciones por request y sigue sin resolver la ambigüedad del token sin `kid`.

### 3. Cachear la clave resuelta cuando el token no trae `kid`

Resolver una vez y guardar el `kid` derivado en el caché Redis.

**Desventajas:**
- Ata el caché de JWKS al primer token visto: un atacante que envíe un token sin `kid`Refresh el JWKS y poison el caché con un `kid` arbitrario.

## Decisión

Se adopta la opción 1.

- Nueva excepción `common/exception/UnknownKeyException` (extiende `InvalidJwtException`) para distinguir "no encontré la clave" de los demás fallos de decodificación.
- `resolvePublicKey`:
  - `entries.isEmpty()` → `UnknownKeyException("JWKS sin claves")`.
  - `keyId` vacío → `singleRsaEntry`: exige exactamente una clave RSA; si hay 0 o >1 → `InvalidJwtException("token sin kid y JWKS ambiguo: N claves RSA")`.
  - `keyId` presente → `.filter(e -> keyId.equals(e.kid()))` con `orElseThrow(UnknownKeyException)`.
  - El chequeo `kty == RSA` sigue lanzando `InvalidJwtException` (no dispara evict: una clave EC no se arregla refrescando).
- `verifyWithRetry` captura `UnknownKeyException | SignatureException`, hace evict y reintenta una vez. `UnknownKeyException` en el reintento se propaga sin envolver para conservar el mensaje específico.
- `keyId.isEmpty()` en lugar de `null`: `JsonNode.asText()` sobre un nodo ausente devuelve `""`, no `null`, y un JWK con `kid: ""` no debe ser matcheable por la rama de `kid` presente.

## Consecuencias

- JWT con `kid` no presente en el JWKS (tras refresh) → `InvalidJwtException` → 401.
- JWT sin `kid` contra JWKS con 0 o >1 claves RSA → 401 con mensaje `token sin kid y JWKS ambiguo`.
- JWT sin `kid` contra JWKS con exactamente 1 clave RSA → válido (compatibilidad con IdPs que no emiten `kid`).
- La rotación de claves del IdP sigue funcionando vía evict + refetch: un `kid` nuevo ausente del caché se resuelve tras el refresh.
- "JWKS sin claves" ahora sí refresca el caché; antes moría sin evict.
- Un token basura con `kid` aleatorio ya no provoca refetch al IdP tras agotado el reintento.
