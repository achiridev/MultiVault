# ADR-0016: Control de abuso del endpoint de onboarding

- **Estado:** ACEPTADA
- **Fecha:** 2026-10-05
- **Decisión:** Triple control sobre `POST /api/v1/tenants` — rate limiting distribuido por IP con corte global, `Idempotency-Key` y aprovisionamiento asíncrono vía Redis Streams.
- **Opciones descartadas:** solo rate limiting; contadores en Postgres; captcha; proof-of-work adaptativo; bucket limitador local sin Redis.

## Contexto

`POST /api/v1/tenants` es el único endpoint `permitAll` de `SecurityConfig` y el riesgo
residual que dejó abierto ADR-0015:

> `POST /api/v1/tenants` sigue sin rate limiting, así que sigue siendo un vector de
> amplificación (Flyway por request) bastante más caro que el probe.

Cada request anónimo paga, **de forma síncrona**:

| Costo | Detalle |
|---|---|
| 1-3 s de CPU/IO | ciclo completo de Flyway sobre `classpath:db/tenant` |
| 1 | `CREATE SCHEMA` en la instancia de Postgres compartida por todos los tenants |
| 5 | `INSERT` (`tenant`, `tenant_identity_provider`, `api_key`, `audit_log`, `subscription`) |
| 1 | egress HTTPS al probe anti-SSRF de `jwks_uri` |

El límite real del daño no es "requests por minuto" sino **schemas creados**. Un atacante
con N direcciones consume N schemas sobre la misma instancia.

Además, dos trampas de diseño que condicionan la solución:

- El estado del bucket limitador **no puede escribir en `audit_log`** por request rechazado:
  un `INSERT` por request de flood sería la misma amplificación que se está cerrando.
- Si Redis no está disponible y el limitador falla abierto, se vuelve al estado actual.

## Opciones consideradas

### Opción 1: rate limiting por IP con contadores en Postgres

**Ventajas:**
- Sin dependencia nueva; el estado es transaccional.

**Desventajas:**
- Un `UPDATE` por request en la base de datos más saturada del sistema.
- `SELECT ... FOR UPDATE` como camino caliente; contención immediate.
- El corte global por aplicación se vuelve un advisory lock.

### Opción 2: rate limiting local en memoria

**Ventajas:**
- Cero latencia, cero dependencias.

**Desventajas:**
- Cada réplica lleva su propio contador: un atacante con N réplicas multiplica su
  presupuesto por N.
- Se conserva como *fallback*, no como backend principal (ver Decisión).

### Opción 3: captcha en el onboarding

**Ventajas:**
- Eficaz contra bots automatizados sin coste de CPU propio.

**Desventajas:**
- Dependencia de terceros, PII y secreto que gestionar.
- Una llamada saliente en el camino del request: en este repo el egress ya es
  superficie de riesgo por el precedente anti-SSRF de ADR-0015.
- Fricción para el usuario legítimo desde el primer request.

### Opción 4: proof-of-work adaptativo

**Ventajas:**
- Sin terceros, sin PII, asimétrico: 4 ms al usuario legítimo, ~200 ms al bot.

**Desventajas:**
- El endpoint de challenge es superficie de ataque nueva y necesita su propio
  rate limit.
- La verificación es entrada no confiable: sin un deadline duro, el atacante
  invierte la amplificación y hace calcular SHA-256 dentro de nuestro request.
- No aporta nada mientras el problema real es el coste de `CREATE SCHEMA` + Flyway.

### Opción 5: triple control (rate limit + idempotencia + aprovisionamiento asíncrono)

**Ventajas:**
- Cierra el vector en su raíz: el request anónimo deja de pagar Flyway.
- Sobrevive a un atacante distribuido, cosa que el rate limit por IP no puede.
- Cada pieza es reversible por separado.

**Desventajas:**
- Rompe el contrato de `POST /api/v1/tenants` (`201` → `202`).
- Introduce una cola cuya durabilidad hay que defender explícitamente.

## Decisión

Se adopta la **opción 5**, con Bucket4j sobre Redis como backend distribuido
(`bucket4j_jdk17-core`, `bucket4j_jdk17-redis-common`, `bucket4j_jdk17-lettuce`).

### 1. Rate limiting distribuido

Reglas declarativas por método + ruta, compiladas a `RequestMatcher` de Spring
Security para no duplicar la tabla de rutas de `SecurityConfig`.

| Regla | Patrón | Scopes | Spec |
|---|---|---|---|
| `onboarding` | `POST:/api/v1/tenants` | IP + GLOBAL | 3 tokens / 1 h |
| `onboarding-global` | `POST:/api/v1/tenants` | GLOBAL | 200 tokens / 1 h |
| `api-default` | `/api/**` | IP | 300 tokens / min |

El bucket `GLOBAL` es un **circuit breaker de la aplicación**: por más que el atacante
rote direcciones, no se crean más de 200 tenants por hora. Es el límite que realmente
ata la factura de infraestructura.

Scopes múltiples se evalúan con semántica AND y fail-fast: el primero que rechaza
corta sin consumir los siguientes.

El filtro por IP se registra **antes** de `ApiKeyAuthenticationFilter`, no después de
un filtro de autenticación. El motivo es concreto: 10k requests con API keys inválidas
deben cortarse antes de tocar el caché `apiKeys`, la base de datos o el JWKS del IdP del
tenant — exactamente el camino que cerró ADR-0014.

**Claves hasheadas.** `HMAC-SHA256(keySalt, regla:scope:valor)` con el salt por variable
de entorno. Dos objetivos: el dump de Redis no expone IPs, y el atacante no puede
enumerar ni pre-computar claves. El valor crudo nunca se loguea.

**Expiración automática.** `ExpirationAfterWriteStrategy.fixedTimeToLive(longestRefillPeriod + 2min)`.
Sin esto, un atacante que rota direcciones escribe una clave por IP para siempre y
convierte el rate limiter en un OOM de Redis.

### 2. fail-closed con fallback local

`FailModeRateLimiter` decora al limiter distribuido. Ante un `DataAccessException` de
Redis y `fail-mode: CLOSED` (default), degrada a `LocalRateLimiter`: un bucket en
memoria por instancia.

"Fail-closed" aquí significa **nunca servir tráfico sin límite**. Se descartaba la
semántica de "denegar con 503" porque convertir una caída de Redis en una caída total
del onboarding no compra protección adicional: los cachés de `apiKeys` y `jwks` ya están
caídos y la aplicación está degradada de todos modos. `fail-mode: OPEN` existe como
opt-in explícito por propiedad.

### 3. Idempotency-Key

Header `Idempotency-Key: <uuid>` en `POST /api/v1/tenants`.

| Estado | Respuesta |
|---|---|
| `SET NX` gana | Se procesa; al completar, `COMPLETED` (TTL 24 h) |
| `IN_PROGRESS` | `409` + `Retry-After: 2` |
| `COMPLETED`, fingerprint igual | Replay del body + `Idempotency-Replayed: true` |
| `COMPLETED`, fingerprint distinto | `422` |

`fingerprint = SHA-256(método + ruta + SHA-256(body))`.

**La garantía real es la base, no Redis.** `schema_name` es `UNIQUE`: si el TTL del claim
expira mientras corre el aprovisionamiento, el segundo request choca con la restricción.
Redis es la optimización, Postgres es el invariante — coherente con el principio de que
la lógica de base vive en la base.

Solo se persisten respuestas `2xx` para replay; un `4xx/5xx` libera la clave para que el
cliente pueda reintentar tras corregir.

El cuerpo se bufferiza explícitamente en el filtro en vez de usar
`ContentCachingRequestWrapper` porque el fingerprint se calcula **antes** de que el
controlador lea el body; sin buffer previo, todas las peticiones compartirían un
fingerprint vacío y ninguna reutilización de clave sería detectada.

### 4. Aprovisionamiento asíncrono

```
REQUEST THREAD (5 INSERT + 1 XADD, sin Flyway, sin CREATE SCHEMA)
  1. validar plan activo
  2. jwksProvider.probe(jwksUri)        ← síncrono, ver abajo
  3. initialize(...)  5 INSERT, status = PENDING_PROVISIONING
  4. issueInitialCredentialsAndRequestProvisioning(...)  1 INSERT api_key
  5. → 202 Accepted

WORKER (Redis Streams)
  1. tenantSchemaProvisioner.provision(schemaName)   CREATE SCHEMA + Flyway
  2. activateIfPending(tenantId, planId)            → ACTIVE + audit TENANT_CREATED
  3. XACK
```

**El probe de `jwks_uri` se mantiene síncrono, deliberadamente.** Diferirlo al worker
haría que un `jwks_uri` inválido se descubriera de forma asíncrona, lo que rompe el
contrato de error que ADR-0015 fijó a propósito (un único mensaje para tres estados
distintos). El coste dominante era Flyway, no un GET, y el rate limit acota el peor caso
a ~200 egress por hora.

**La API key inicial se devuelve en el `202`.** La alternativa —no devolverla y que el
cliente haga polling con un token opaco— exige un endpoint anónimo nuevo, almacenamiento
one-time y su propia regla de rate limit: más superficie y más trabajo. Con la key
devuelta, el `409` del filtro de tenant es la señal de polling mientras el schema aún no
existe, y no hace falta ningún endpoint nuevo.

**El encolado es AFTER_COMMIT**, con el patrón ya establecido por ADR-0003. Un `XADD`
dentro de la transacción se perdería en un rollback; commit seguido de `XADD` deja una
ventana de pérdida si el proceso muere entre medias.

**Redis Streams no es una base de datos.** Un `FLUSHDB` —o perder la instancia de
caché— elimina caché *y* cola. Por eso `PENDING_PROVISIONING` en Postgres es la fuente
de verdad y `ProvisioningReconciler` reconstruye la cola cada `reconcile-interval` para
los tenants que llevan más de `stale-after` en ese estado.

**Reintentos.** Entrega at-least-once: si el worker muere entre `provision()` y `XACK`, el
mensaje se vuelve a reclamar. Ambas operaciones son idempotentes
(`CREATE SCHEMA IF NOT EXISTS` + `Flyway.migrate()`), y la activación es un
**UPDATE condicional** sobre `PENDING_PROVISIONING`: `rowsAffected == 1` publica el audit,
`== 0` no. Un setter duplicaría `TENANT_CREATED` en cada redelivery.

Un fallo reencola el job con `attempt + 1` hasta `max-attempts`; agotados, el tenant queda
`SUSPENDED`, se emite `TenantProvisioningFailedEvent` y el job va a un stream de dead
letter. Los mensajes con worker caído se recuperan con `XPENDING` + `XCLAIM` por
`visibility-timeout`; no se hace `CLAIM` sobre lo recién entregado porque su idle time es
cero y el min-idle-time lo filtraría, dejando el mensaje pendiente para siempre.

### 5. Puerta de estado

`TenantSchemaResolver` ya hacía `tenantRepository.findById(tenantId)` en **cada** request
autenticado y solo leía `getSchemaName()`. Leer `getStatus()` es I/O adicional cero, así
que un tenant que no está `ACTIVE` responde `409` (`Retry-After: 2` si está
`PENDING_PROVISIONING`) en el mismo punto donde antes fallaría con un error 500 al no
existir el schema.

## Consecuencias

**Positivas:**
- Un request anónimo deja de pagar `CREATE SCHEMA` ni Flyway.
- El corte global ata la factura de infra con independencia de cuántas IPs se usen.
- Los replays y reintentos de red son gratuitos.
- Una caída de Redis degrada a límite por instancia, nunca a tráfico ilimitado.
- `audit_log.ip_address` pasa a registrar la IP real detrás de un proxy: antes registraba
  la del load balancer, lo que lo hacía inútil para investigar abuso.

**Negativas:**
- `POST /api/v1/tenants` cambia de `201` a `202`. Los clientes que esperen un tenant
  utilizable de inmediato reciben `409` hasta que el worker termina.
- El catálogo de `plan` queda sin enforcement: `max_requests_per_minute` sigue sin leerse.
  Deliberado — meter una lectura de `plan` en el camino caliente es I/O por request para
  una cuota de *fair use*, no de abuso. Se resuelve por scope `API_KEY` en el servicio de
  cuotas, no en el filtro.
- Redis pasa a ser dependencia de disponibilidad, no solo de rendimiento.
- El soporte de Redis Cluster queda fuera: la configuración de Bucket4j exige standalone.
- Los buckets del fallback local no se comparten entre réplicas, así que durante una caída
  de Redis el límite efectivo es `capacity × instancias`.
