# ADR-0019: Key de bootstrap con scopes acotados (reemplaza ADR-0012)

- **Estado:** ACEPTADA
- **Fecha:** 2026-10-11
- **Decisión:** Al crear un tenant (`POST /api/v1/tenants`), se emite una `API key` de tipo `SERVICE`, sin TTL (`expires_at = null`, nunca expira), con scopes `api_keys:read, api_keys:manage, tenant:settings:write`. Esta key es la raíz de confianza del tenant y permite administrar la configuración y emitir nuevas keys, pero no opera directamente sobre documentos.

## Contexto

El ADR-0012 establecía la key inicial como `SERVICE` con `scope = ["*"]`, lo que otorgaba acceso a todo el catálogo (`documents:read/write/delete`, `folders:*`, `permissions:*`, `audit:read`, `system:*`, etc.). Aunque funcional, esto viola el principio de menor privilegio: una credencial entregada por un endpoint anónimo tiene acceso total sin límite temporal y sin mecanismo de revocación individual (el único control era revocar todas con `CANCEL`).

Además, el argumento de ADR-0018 línea 22 ("con la llave maestra un tenant sin IdP puede crear documentos") queda invalidado con esta decisión: sin `documents:write` en la raíz, no se pueden crear documentos sin antes configurar el `identity_provider` y emitir una key derivada con ese scope. Esto refuerza, no debilita, la obligatoriedad del IdP (ADR-0006, ADR-0018).

El plan de implementación define: `F0 ADR-0019 → F1 migración V3 → F2 Scopes (sin *) → F3 CurrentTenant → F4 servicio → F5 controller → F6 caché → F7 rate limit → F8 tests → F9 docs`. El cambio de código ya está aplicado al servicio (`ApiKeyService.createInitial`); los pasos F4-F5 corresponden a los endpoints de gestión de keys (`POST /api/v1/api-keys` con `api_keys:manage`), que se implementarán en una fase posterior cuando la raíz de confianza esté validada.

## Decisión

Se adopta la Opción E del análisis previo (reducida y precisa):

1. **Key inicial (`createInitial`)**: `SERVICE`, `scopes = ["api_keys:read", "api_keys:manage", "tenant:settings:write"]`, sin TTL.
2. **Sin `*`**: El wildcard se elimina del catálogo (`Scopes.java`) y un `CHECK` en la base de datos (`chk_no_wildcard_scope`) prohíbe almacenarlo. La defensa es estructural, no solo de aplicación (`ApiKeyScopeValidator`).
3. **Una sola key `manage` por tenant**: La restricción se garantiza a nivel de servicio (`ApiKeyService.create`) y se protegé con `EstadoTransicionInvalidoException` al intentar revocar la última activa, evitando el lockout del tenant.
4. **Atribución de actor**: Las keys emitidas por la raíz registran `created_by_api_key_id` (referencia a la key creadora); las emitidas por un humano (`STANDARD` + JWT) registran `created_by_user_id`. Ambos cumplen el `CHECK chk_api_key_actor`.
5. **Expiración configurable**: El usuario decide `expiresAt` por key (incluido `null` = nunca expira) a través del endpoint `POST /api/v1/api-keys` (próxima fase).

## Consecuencias

- **Positivas**: La raíz de confianza se limita a la administración del tenant y la emisión de credenciales. El acceso a datos requiere una key derivada con scopes específicos (`documents:*`, etc.), que es revocable individualmente y auditada (`API_KEY_CREATED`, `API_KEY_REVOKED`). La revocación individual funciona con `ApiKeyCacheEvictor` (el bug previo del caché Redis se corrige).
- **Negativas / Aceptadas**: La raíz sigue siendo una credencial de `curl` sin verificación nominal del admin (ADR-0018 intacto). Un tenant sin `identity_provider` configurado **no puede crear documentos** (la línea 22 de ADR-0018 queda invalidada), reforzando la obligatoriedad del IdP (ADR-0006, ADR-0015). El endpoint `POST /api/v1/api-keys` aún está pendiente (F4-F5), por lo que hoy la raíz solo administra; los documentos seguirán operando con la root hasta que ese endpoint esté disponible, momento en el que se aplicará el modelo completo de derivación de credenciales.
