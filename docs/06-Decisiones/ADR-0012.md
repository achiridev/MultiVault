# ADR-0012: API key inicial SERVICE como llave maestra; tenant derivado del principal

- **Estado:** Aceptada
- **Fecha:** 2026-08-29
- **Decisión:** La API key inicial del onboarding nace como `SERVICE` con scope `*` (llave maestra que expande a todo el catálogo de scopes). Los endpoints de configuración del tenant (`identity-provider`, `status`) se restringen a credenciales SERVICE y derivan el `tenantId` del principal autenticado, **ignorando el path**, eliminando así el riesgo de IDOR cross-tenant.
- **Opciones descartadas:** key inicial STANDARD con scopes vacíos; mantener el `{tenantId}` en el path validándolo contra el principal.

## Contexto

El ADR-0011 dejó la key inicial del onboarding como `STANDARD` con `scopes = []`. Con el requisito de que el JWT de tenant siempre viaja con una key STANDARD (ADR-0011), esa key inicial era **inutilizable sola**: no tiene JWT asociado ni scopes, por lo que todo endpoint con `@PreAuthorize` respondía 403. El onboarding entregaba al cliente una credencial que no podía administrar nada.

Además, `TenantController` exponía los endpoints `PUT /tenants/{tenantId}/identity-provider` y `PUT /tenants/{tenantId}/status` tomando el `tenantId` directamente del path, sin cruzarlo contra el tenant de la credencial autenticada. Un cliente con una credencial válida de cualquier tenant podía reconfigurar el OIDC (`jwks_uri`, `issuer`, `audience`) o cambiar el estado de otro tenant si conocía su UUID — un vector IDOR.

Estos endpoints son de naturaleza machine-to-machine: no hay un usuario humano razonando sobre ellos, configuración de OIDC y estado de tenant los opera el propio sistema/proceso del tenant. Por eso la credencial correcta es una API key `SERVICE` (sin JWT), no una STANDARD+JWT ni un `TenantUserPrincipal`.

## Opciones consideradas

### 1. Key inicial SERVICE maestra + tenant del principal (seleccionada)

- `ApiKeyService.createInitial` crea la key como `SERVICE` con `scopes = ["*"]`.
- El wildcard `*` se expande en `ApiKeyAuthenticationFilter` (y en la combinación STANDARD+JWT) al catálogo completo de scopes (`Scopes.all()`), convirtiéndose en authorities reales `SCOPE_<scope>`.
- `TenantController` deriva el `tenantId` de `CurrentTenant.serviceTenantId()`, que solo acepta un `ApiKeyPrincipal` de tipo `SERVICE`; cualquier otra credencial (STANDARD+JWT, JWT puro) responde 403.
- Las rutas pierden el segmento `{tenantId}`: `PUT /tenants/identity-provider` y `PUT /tenants/status`.

**Ventajas:**
- La key maestra es funcional desde el arranque: un tenant recién creado puede administrar su propia configuración sin humanos ni JWT.
- Cierra el IDOR: un proceso solo opera sobre su propio tenant, sea cual sea su UUID.
- Unifica el catálogo de scopes en una fuente de verdad (`Scopes`) para la key maestra, el wildcard y la futura validación de creación de keys.
- ENDPOINTS service-to-service: sin mezcla de identidades humanas.

**Desventajas:**
- Cambio de contrato: las rutas dejan de llevar `tenantId` (breaking).
- La key inicial cambia de tipo: de `STANDARD` a `SERVICE`; el cliente debe tratarla como credencial de servicio (sin JWT).
- Los endpoints de tenant-settings quedan fuera del alcance de credenciales STANDARD+JWT (un `TenantUserPrincipal` no puede invocarlos); los documentos siguen aceptando STANDARD+JWT.

### 2. Mantener el path y validar path == tenant del principal

**Ventajas:**
- Sin cambio de ruta.

**Desventajas:**
- Sigue arrastrando el `{tenantId}` en el path (superficie innecesaria), y la validación se vuelve manual en cada controller en vez de resolverlo de la credencial.

## Decisión

Se adopta la opción 1.

- Nueva clase `infrastructure/security/apikey/Scopes.java`: catálogo central de scopes + `all()` + `WILDCARD`.
- `ApiKeyAuthenticationFilter` y `JwtAuthenticationFilter` expanden `*` a `Scopes.all()`.
- `ApiKeyService.createInitial`: `key_type = SERVICE`, `scopes = ["*"]`.
- Nueva clase `infrastructure/security/CurrentTenant#serviceTenantId()`: devuelve el `tenantId` del `ApiKeyPrincipal` si es `SERVICE`; en caso contrario lanza `AccesoDenegadoException` (403).
- `TenantController`: rutas `identity-provider` y `status` sin `{tenantId}`, conservan `@PreAuthorize("hasAuthority('SCOPE_tenant:settings:write')")`.
- `SecurityConfig`: matchers a rutas concretas (`identity-provider`, `status`), sin el comodín `*` del path.

## Consecuencias

- `POST /api/v1/tenants` responde la API key inicial con `key_type = "SERVICE"` y scope `*` (antes `STANDARD` sin scopes).
- Los endpoints `PUT /api/v1/tenants/identity-provider` y `PUT /api/v1/tenants/status` ya no reciben `{tenantId}`; el tenant operado es siempre el del principal SERVICE.
- Un request con STANDARD+JWT o JWT puro a esos endpoints responde `403` (no `401`): la credencial autenticó pero el tipo no es SERVICE.
- El scope `tenant:settings:write` lo ejerce la key SERVICE del propio tenant. Un futuro `SUPER_ADMIN` (platform_staff) gestionará cualquier tenant por su propio canal (pendiente), sin reutilizar estas claves.
- Cuando exista el endpoint de creación de API keys, hay que validar los scopes contra el catálogo `Scopes` (constraint/check en BD). Pendiente (ADR-0011).
