# ADR-0012: API key inicial SERVICE como llave maestra; tenant derivado del principal

- **Estado:** SUSTITUIDA por ADR-0019
- **Fecha:** 2026-08-29
- **Decisión:** La API key inicial del onboarding nace como `SERVICE` con scope `api_keys:read, api_keys:manage, tenant:settings:write` (no `*`). Los endpoints de configuración del tenant (`identity-provider`, `status`) se restringen a credenciales SERVICE y derivan el `tenantId` del principal autenticado, sin path, eliminando así el riesgo de IDOR cross-tenant.

## Contexto

El ADR-0011 dejó la key inicial del onboarding como `STANDARD` con `scopes = []`. Con el requisito de que el JWT de tenant siempre viaja con una key STANDARD (ADR-0011), esa key inicial era **inutilizable sola**: no tiene JWT asociado ni scopes, por lo que todo endpoint con `@PreAuthorize` respondía 403. El onboarding entregaba al cliente una credencial que no podía administrar nada.

Estos endpoints son de naturaleza machine-to-machine: no hay un usuario humano razonando sobre ellos, configuración de OIDC y estado de tenant los opera el propio sistema/proceso del tenant. Por eso la credencial correcta es una API key `SERVICE` (sin JWT), no una STANDARD+JWT ni un `TenantUserPrincipal`.

## Opciones consideradas

### 1. Key inicial SERVICE maestra + tenant del principal (seleccionada)

- `ApiKeyService.createInitial` crea la key como `SERVICE` con `scopes = ["api_keys:read", "api_keys:manage", "tenant:settings:write"]`.
- El wildcard `*` se elimina del catálogo y un CHECK en BD prohíbe almacenarlo.
- Los scopes se expanden por `Scopes.all()` en `ScopeAuthorities` para convertir `*` a autoridades reales `SCOPE_<scope>`.
- `TenantController` deriva el `tenantId` del `CurrentTenant.serviceTenantId()`, que solo acepta un `ApiKeyPrincipal` de tipo `SERVICE`.
- Los endpoints `identity-provider` y `status` pierden el segmento `{tenantId}`: `PUT /tenants/identity-provider` y `PUT /tenants/status`.
- Las rutas de tenant-settings quedan fuera del alcance de credenciales STANDARD+JWT (un `TenantUserPrincipal` no puede invocarlos); los documentos siguen aceptando STANDARD+JWT.
- Cuando exista el endpoint de creación de API keys, hay que validar los scopes contra el catálogo `Scopes` (constraint/check en BD). Pendiente (ADR-0011).
- Cuando exista el endpoint de creación de API keys, hay que validar los scopes contra el catálogo `Scopes` (constraint/check en BD). Pendiente (ADR-0011).
- Cuando exista el endpoint de creación de API keys, hay que validar los scopes contra el catálogo `Scopes` (constraint/check en BD). Pendiente (ADR-0011).

### 2. Mantener el path y validar path == tenant del principal

**Ventajas:**
- Sin cambio de ruta.

**Desventajas:**
- Sigue arrastrando el `{tenantId}` en el path (superficie innecesaria), y la validación se vuelve manual en vez de resolverlo de la credencial.

## Decisión

Se adopta la opción 1.

- Nueva clase `infrastructure/security/apikey/Scopes.java`: catálogo central de scopes + `all()` + `WILDCARD` (prohibido por CHECK en BD).
- `ApiKeyService.createInitial`: `key_type = SERVICE`, `scopes = ["api_keys:read", "api_keys:manage", "tenant:settings:write"]`.
- `TenantController`: rutas `identity-provider` y `status` sin `{tenantId}`, conservan `@PreAuthorize("hasAuthority('SCOPE_tenant:settings:write')")`.
- `SecurityConfig`: matchers a rutas concretas (`identity-provider`, `status`), sin el comodín `*` del path.

## Consecuencias

- `POST /api/v1/tenants` responde la API key inicial con `key_type = "SERVICE"` y scope `api_keys:read, api_keys:manage, tenant:settings:write` (antes `STANDARD` sin scopes).
- Los endpoints `PUT /api/v1/tenants/identity-provider` y `PUT /api/v1/tenants/status` ya no reciben `{tenantId}`; el tenant operado es siempre el del principal autenticado.
- Un request con STANDARD+JWT o JWT puro a esos endpoints responde `403` (no `401`): la credencial autenticó pero el tipo no es SERVICE.
- El scope `tenant:settings:write` lo ejerce la key SERVICE del propio tenant. Un futuro `SUPER_ADMIN` (platform_staff) gestionará cualquier tenant por su propio canal (pendiente), sin reutilizar estas claves.
- Cuando exista el endpoint de creación de API keys, hay que validar los scopes contra el catálogo `Scopes` (constraint/check en BD). Pendiente (ADR-0011).
- El scope `*` se expande por `Scopes.all()` → autoridades reales `SCOPE_<scope>`, deduplicadas.
- La auditoría registra `API_KEY_CREATED` y `API_KEY_REVOKED` con metadata que incluye scopes y TTL (o ausencia de TTL).
