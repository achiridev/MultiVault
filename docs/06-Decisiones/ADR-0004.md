# ADR-0004: Aprovisionamiento de schema por tenant con Flyway programático

- **Estado:** Aceptada
- **Fecha:** 2026-08-06
- **Decisión:** El schema de cada tenant se crea y migra en runtime con una instancia Flyway programática (`classpath:db/tenant`), fuera de la transacción de onboarding.
- **Opciones descartadas:** Ejecución directa del SQL vía `JdbcTemplate`, migración dentro del `@Transactional` de creación.

## Contexto

El flujo de creación de tenant necesita crear el schema físico (`CREATE SCHEMA`) y aplicar el template `tenant_schema.sql` (carpetas, documentos, versiones, permisos) para que el tenant quede operativo (`status = ACTIVE`). ADR-0001 definió schema-per-tenant y dejó pendiente el mecanismo de aprovisionamiento. Surgen dos restricciones:

- Flyway abre su propia conexión: no participa en la transacción de Spring, por lo que no puede ejecutarse dentro del `@Transactional` que inserta las filas de `public`.
- El `AuditLogEventListener` de ADR-0003 es `AFTER_COMMIT`: el evento `TENANT_CREATED` debe publicarse desde una transacción que haga commit.

## Opciones consideradas

### 1. Flyway programático por tenant (seleccionada)

El template se versiona como `db/tenant/V1__tenant_schema.sql`. Al aprovisionar: `CREATE SCHEMA IF NOT EXISTS` + `Flyway.configure().dataSource(ds).schemas(schema).locations("classpath:db/tenant").load().migrate()`.

**Ventajas:**
- Historial de migraciones por schema (`flyway_schema_history` dentro del schema del tenant) → futuras migraciones por tenant son aditivas y versionadas (regla del proyecto)
- Consistente con el manejo del schema `public` (mismo motor Flyway)
- El nombre de schema se valida con regex (`^[a-z][a-z0-9_]*$`) antes de ejecutar DDL

**Desventajas:**
- Mayor latencia en el onboarding (conexión + migración) — aceptable para un flujo de aprovisionamiento
- Costo de infraestructura Flyway (una instancia por tenant al aprovisionar)

### 2. Ejecución directa con JdbcTemplate

**Ventajas:**
- Sin overhead de Flyway

**Desventajas:**
- Sin historial de migraciones por schema
- No versionado: cambios futuros al schema de tenant requieren scripts manuales idempotentes

### 3. Migración dentro del `@Transactional` de creación

**Desventajas:**
- Flyway usa conexión propia → el schema y las filas de `public` se comprometen en transacciones distintas sin control
- Si la migración falla, el rollback de Spring no revierte el schema (DDL de Flyway ya committeado en su conexión)

## Decisión

Se adopta **Flyway programático por tenant** con tres límites transaccionales en el onboarding:

1. TX 1 (`TenantProvisioningService.initialize`): inserta `tenant` (`PENDING_PROVISIONING`), `subscription` (`ACTIVE`), `tenant_usage`, `tenant_member` e `identity_provider` (opcional).
2. Fuera de transacción (`TenantSchemaProvisioner.provision`): `CREATE SCHEMA` + Flyway con `locations("classpath:db/tenant")`. Si falla → `TenantProvisioningService.markProvisioningFailed` (tenant `SUSPENDED` + `suspended_reason`) + evento `TenantProvisioningFailedEvent` para notificar.
3. TX 2 (`TenantProvisioningService.activate`): tenant `ACTIVE` + `current_plan_id`, API key inicial del admin (`ApiKeyService.createInitial`) y auditoría `TENANT_CREATED` (AFTER_COMMIT).

## Consecuencias

- `TenantService.create` deja de ser transaccional (orquestador); la atomicidad se mantiene por etapas con estados intermedios observables (`PENDING_PROVISIONING`, `SUSPENDED`).
- `tenant_schema.sql` se movió a `src/main/resources/db/tenant/V1__tenant_schema.sql` (formato Flyway versionado). El Flyway principal de `public` (`classpath:db/migration`) no la escanea.
- El rol de BD debe tener permiso `CREATE SCHEMA` sobre el esquema de la conexión.
- Notificación al admin ante fallo: por ahora evento + log; el canal real (email/webhook) queda pendiente.
- Retry manual de aprovisionamiento fallido requiere operación ad-hoc (reintentar migración y activar).
